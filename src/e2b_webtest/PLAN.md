# Plan: `e2b-webtest` -- sandbox an adaptive Playwright testing agent for a project's web stack

## Context

You want a way for me to actually test your app -- not just read code and guess, but drive a
real browser against it and react to what I find. The open question was *where* that needs to
happen. Two very different things were being lumped together under "testing":

1. **A Playwright script I write in advance.** This is just code. You read it, you run it
   yourself, you show me the results. There is no point at which I act on your machine -- the
   script is inert text until you execute it, exactly like any other file I hand you. Sandboxing
   this buys you nothing regarding *danger*, because there's no autonomous action to contain.
2. **An adaptive agent** -- Claude Code running headlessly, deciding turn-by-turn what to do
   next with Bash and file-system access, no human reviewing each action before it happens. Run
   *that* locally and it can read your `.env` files, hit your real database, install things, or
   touch anything else on your machine -- because nothing previewed its actions first. This is
   the actual "computer use" risk, and it's the reason a disposable, contained sandbox matters.

So the tool is scoped to the thing that actually needs containing: **`e2b-webtest` exists
purely to run the adaptive agent, in an E2B sandbox, against a project's full web stack.**
Static Playwright scripts are a separate, tool-free workflow -- I write the script, you run it
locally against your own already-running dev environment, no upload/sandbox/CLI involved at
all.

Ground rules (from you, unchanged):
- **No app, browser, container, or E2B activity on your machine from Claude.** For the sandboxed
  agent, I write the code and run only the tool's mocked unit tests locally; the agent itself
  runs in E2B, and you trigger those live runs. For local script testing, I write the script and
  you run it -- I never execute it myself, locally or otherwise.
- **Claude never touches env files or the local database.** The tool never opens `.env*` files
  and never connects to local Supabase, in the sandbox or on your machine. Any step that needs
  them is an instruction for you to run.
- **We build it together.** Each milestone ends with commands for you to run. You report the
  result, then we continue.
- **No secret values ever printed.** `up` and any command that sends environment variables into
  the sandbox show their **names only** and wait for your approval first (already built, in
  `envs.py`).

Decisions made while planning:
- **Local scripts and the sandboxed agent are no longer parallel features of the same tool.**
  Local scripts need nothing from `e2b-webtest` -- I write a Playwright script or test file,
  explain how to run it (`pytest`, `npx playwright test`, whatever the project already uses),
  and you run it against your own local dev stack the way you normally would. `e2b-webtest`'s
  entire job becomes running the **agent** -- Claude Code itself (`claude -p`, not the Playwright
  MCP server) -- headlessly inside a disposable sandbox, with Bash + file tools, driving a real
  Playwright browser it writes/runs itself, for open-ended or exploratory testing where a fixed
  script isn't enough.
- Credentials: **AWS Bedrock with a temporary, ~1-hour STS session credential**, not a Console
  API key and not `claude setup-token`. `claude setup-token` was the first idea (backed by your
  Pro subscription, so no separate billing account) but it's a **fixed one-year token with no TTL
  flag and no documented revocation path** -- not acceptable to send anywhere, even into a
  disposable sandbox. Bedrock's `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`
  triple, generated by **you** with `aws sts get-session-token --duration-seconds 3600` (or an
  assumed role with a 1-hour session), expires on its own after an hour -- no manual revocation
  needed, and Claude Code's Bedrock integration is documented to handle time-limited credentials
  correctly (it re-resolves before they expire). All three values cross into the sandbox through
  the **existing approval gate**, same as any other forwarded variable; `CLAUDE_CODE_USE_BEDROCK=1`,
  `AWS_REGION`, and `ANTHROPIC_MODEL` (a Bedrock model id, not a plain alias -- see Risks) are not
  secret and go in `env.set` instead. **Prerequisite**: your AWS account needs Bedrock model
  access for a Claude model enabled first (a one-time setup in the AWS Bedrock console, on your
  side) -- flagged in the milestone below, not something to discover mid-run.
- Hard usage limits, because nothing supervises this run once it starts: every `agent` invocation
  passes **both** `--max-turns` and `--max-budget-usd`, so the CLI itself stops the run once
  either is hit, independent of whether the agent ever gets to write its own report. Defaults
  `--max-turns 30 --max-budget-usd 2.00`, overridable per run (`e2b-webtest agent <task-file>
  --max-turns N --max-budget-usd N`) -- starting points, to be tuned once we see real runs.
- "All results saved" does not depend on the run ending cleanly: `agent.py` writes **every line
  it streams**, live, to a local raw log file as it arrives -- regardless of whether the process
  later exits 0, hits a turn/budget limit, or crashes. The agent's own `report.md` (below) is the
  readable summary, the raw log is the guarantee that nothing is lost even if a limit cuts the
  run off mid-task.
- The `webapp-testing` skill's patterns are made available **inside the sandbox only** (never
  installed on your machine, per your earlier "I don't want the skill on my machine").
- Dinner Circle runs its **full stack** in the sandbox (Supabase, the backend, and the Expo web
  export) so the agent has something real to test against -- unchanged, already built and
  template-tested.
- Packaging: a Python CLI in this repo (`scoped`-style) plus a per-project TOML config --
  unchanged.

## What's new: the in-sandbox agent

### Template changes (`template.py`)
- Node bumped **20 → 22** (Claude Code's documented minimum; Node 20 installs with a harmless
  `EBADENGINE` warning, but 22 avoids it).
- Add `npm install -g @anthropic-ai/claude-code`.
- **Put the Playwright venv on `PATH`** (`set_envs({"PATH": "/home/user/.venv/bin:$PATH"})` or
  equivalent). It matters because the agent will naturally write a script and run `python3
  foo.py`, getting the *system* python with no Playwright in it, unless the venv is already
  first on `PATH`. Left alone, the first agent run burns real turns on `ModuleNotFoundError:
  playwright` and probably tries to `pip install playwright` (needing a Chromium re-download it
  doesn't have room for). The appended task instruction also states the interpreter explicitly,
  as belt and braces.
- Fetch the `webapp-testing` skill at **build time** (E2B's build infrastructure, never your
  machine) into a fixed path, e.g. `/opt/agent-skills/.claude/skills/webapp-testing/`, via
  `npx skills add anthropics/skills@webapp-testing` run in that directory. This is the one
  genuinely uncertain step -- exactly where that installer places files isn't confirmed from
  docs alone, so it's a named risk below, fixed live once we can see the actual layout.
- All of this installs while the builder is still `root` (the same ordering rule the last two
  live bugs taught us), before the existing drop back to `user`.

### How instructions get to the agent
Not a shell-string argument -- a long, multi-line task ("check the anon store-selection flow,
try both stores, sign in, generate a plan, note anything broken or surprising") is awkward and
error-prone as a quoted CLI arg, and impossible to iterate on cleanly. Instead `agent` takes a
**file path**:
```
e2b-webtest agent <task-file>
```
Claude writes the task as an ordinary local `.md` file (e.g. `.e2b-webtest/task.md` -- already
git-excluded by the same mechanism `state.py` uses for `.e2b-webtest/`). `cmd_agent` reads that
file locally (just reading a file Claude itself wrote -- not user data, not a config/secret file)
and passes its text as the `-p` prompt, with one fixed instruction appended (see below).

### How findings get back
Two separate channels, deliberately not conflated:
- **Live progress, for you to watch while it runs**: `--output-format stream-json --verbose`
  streams NDJSON events as the agent works (deliberately *without* `--include-partial-messages`,
  which emits token-level deltas -- message-level events are what's actually wanted here).
  `agent.py`'s `on_stdout` parses each line and renders it the way `scoped/cli.py`'s
  `ScopedSession.send` already renders `AssistantMessage`/`ToolUseBlock`/text (`[tool_name]
  summary`, plain text for talk) -- reused pattern, not reinvented. This is visibility only, not
  how results get captured -- the exact stream-json event schema isn't something to build a
  parser's correctness around sight unseen.
- **The actual findings, reliably**: the fixed instruction appended to every task tells the agent
  to write a structured report -- "when finished, write what you did and found (successes,
  failures, anything unexpected) to `$E2B_WEBTEST_OUTPUT_DIR/report.md`, and save any screenshots
  to the same directory." That directory is pulled back by **`scripts.download_outputs`, reused
  completely unchanged**. No new download/parsing code at all; `report.md` just shows up as one
  more file in `.e2b-webtest/downloads/` alongside the screenshots.
- **The raw guarantee, independent of the above two**: every stream-json line, as it arrives, is
  also appended straight to a local file (`.e2b-webtest/downloads/<task-file-stem>-raw.jsonl`) by
  the orchestrating Python process itself -- not downloaded after the fact, written live as the
  run happens. This exists whether the run finishes cleanly, hits `--max-turns`/`--max-budget-usd`,
  or the sandbox connection drops, because it never depends on the agent (or the sandbox) still
  being alive to hand it over.

Claude reads whichever of these landed locally with the Read tool once you say the run finished
(or stopped) -- the same way it already plans to look at screenshots.

### New module: `agent.py`
- `build_command(task: str, *, max_turns: int, max_budget_usd: float) -> str`: pure, testable --
  constructs `claude -p <task+suffix, shlex-quoted> --dangerously-skip-permissions
  --add-dir /opt/agent-skills --allowedTools "Bash,Read,Write,Edit" --max-turns <n>
  --max-budget-usd <n> --output-format stream-json --verbose`. Never passes `--bare` -- the
  Bedrock credentials would still work under it, but the `webapp-testing` skill's auto-discovery
  would not, and loading the skill is the reason it's there. `--dangerously-skip-permissions`
  refuses to run as root -- confirmed compatible, since the sandbox's runtime user is already
  `user`, non-root, by design.
- `run_agent(sandbox, task_file: Path, upload: UploadConfig, env: dict[str, str], raw_log: Path,
  *, max_turns: int, max_budget_usd: float, timeout: float | None) -> int`: `mkdir -p` the output
  directory and inject `E2B_WEBTEST_OUTPUT_DIR` into the command's env (the same pattern
  `runner.py`'s setup steps already use -- without this the appended instruction interpolates to
  an empty path and the report goes nowhere), reads `task_file`, appends the fixed instruction,
  then runs `build_command`'s output via `sandbox.commands.run(..., cwd=upload.dest, envs=env,
  timeout=timeout, on_stdout=<render + append to raw_log>, on_stderr=...)`. Returns the command's
  exit code without raising on a nonzero one (a limit hit or a failed test session is an expected
  outcome, not a tool error).
- The appended instruction states three things, not one: write the report to
  `$E2B_WEBTEST_OUTPUT_DIR/report.md`, save screenshots to the same directory, and **use
  `/home/user/.venv/bin/python3`** (the interpreter that actually has Playwright).
- `render_event(line: str) -> str | None`: parses one stream-json line for the live-progress
  renderer; pure and unit-testable against fixture event lines, independent of the live run.

### `cli.py`: new `agent` subcommand
```
e2b-webtest agent <task-file> [--max-turns 30] [--max-budget-usd 2.00]
```
Requires a running sandbox (`_require_state`), calls the existing `_approve_env` (so
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` show up by name and need
your yes, exactly like any other forwarded variable -- `--yes` still works to skip it), then
`agent.run_agent` (always, regardless of its exit code, writing the raw log), then
`scripts.download_outputs` and prints the downloaded file names (`report.md` included when the
agent got to write one). You run this command; Claude writes the task file in advance.

### Testing
Same split as everything else: `agent.py`'s command-construction (the exact argv, the env var
names, the stream-json line rendering) is pure and covered by local unit tests against a fake
sandbox -- **no real `claude` invocation, no E2B, no network**. Whether the whole thing actually
works -- Claude Code installing cleanly, the skill loading, the agent successfully driving
Playwright -- is a live milestone, like everything else in E2B.

## What local script testing looks like (no tool, no sandbox)
When a fixed, repeatable check is what's actually needed -- not open-ended exploration -- I
write a Playwright script or test file as an ordinary local file, tell you what it does and how
to run it (e.g. `npx playwright test tests/store-selection.spec.ts`, or a `pytest` invocation,
matching whatever Dinner Circle already uses), and you run it yourself against your own
already-running local dev stack. You share the output/screenshots back and I read them. Nothing
about this touches `e2b-webtest`, E2B, or a sandbox -- it's the same "I write code, you run it"
workflow as everything else we do together.

## Risks
- Supabase's Docker stack at 4 vCPU/8 GiB (milestone 5). Fallback: `supabase start -x studio,inbucket,...`.
- The 10 GiB Hobby disk, now also carrying the Claude Code CLI + skill files -- **checked
  directly, before writing agent.py, in milestone 6** (`df -h`/`du -sh` via `exec`), not assumed.
- The 1-hour Hobby session cap; `extend` covers it (already live-verified via `status`'s `times
  out` field).
- **Where `npx skills add` actually installs the skill**, and whether `--add-dir` needs a
  different path -- **checked directly in milestone 6** (`find / -iname SKILL.md` via `exec`), so
  `agent.py` is written against a confirmed path in milestone 7, not a guess.
- **`--bare` vs. skill auto-discovery**: Claude Code's own docs describe `--bare` as both
  "recommended for CI" and as skipping skill auto-discovery -- `agent.py` does not pass `--bare`,
  specifically so the skill loads; worth confirming live that nothing else assumed by `--bare`
  (fast startup, no CLAUDE.md discovery) turns out to matter.
- Cost: Bedrock is billed on your AWS account, separately from your Claude subscription -- real
  money, metered per token, bounded per run by `--max-turns`/`--max-budget-usd` but not capped
  overall. Worth checking AWS Cost Explorer after the first few runs.
- Bedrock model access is a real prerequisite, not a given: if your AWS account hasn't been
  granted access to a Claude model in the Bedrock console yet, the first `agent` run fails
  immediately on auth/model-not-found, not on anything this tool controls -- checked live in
  milestone 9.
- **Bedrock needs an explicit model id.** `CLAUDE_CODE_USE_BEDROCK=1` and `AWS_REGION` are not
  enough on their own -- Claude Code on Bedrock generally needs `ANTHROPIC_MODEL` set to a
  Bedrock model identifier (the `us.anthropic.claude-...-v1:0` form), since a plain model alias
  isn't a valid Bedrock id. It goes in `env.set` next to the other two (folded into milestone 9
  above). The exact id depends on which model your account has access to in which region, so it
  gets filled in at milestone 9, from what your Bedrock console actually shows.
- The STS credential's ~1-hour TTL roughly matches the sandbox's own default 1-hour timeout,
  which is convenient -- but if you `extend` the sandbox past an hour and run `agent` again
  later, the earlier STS credential will have already expired and needs regenerating (a fresh
  `aws sts get-session-token`, re-approved), which is expected, not a bug.
- Exact exit behavior when `--max-turns`/`--max-budget-usd` is hit isn't confirmed from docs
  alone (does it print a usable partial result, or just error out) -- milestone 9 checks this
  directly. It doesn't threaten the "all results saved" guarantee either way, since the raw log
  is written as events stream in, not reconstructed from the process's final output.
- **`--allowedTools` may be moot under `--dangerously-skip-permissions`.** The narrow toolset
  (`Bash,Read,Write,Edit`, deliberately no `WebFetch`/`WebSearch`) is the intent, but if skipping
  permissions bypasses the allowlist rather than filtering against it, the agent could reach for
  other tools anyway. Inside a disposable sandbox that is not dangerous, but it does weaken the
  "least privilege" claim -- worth watching the milestone 9 raw log for tool calls outside the
  list, and switching to `--permission-mode` if the allowlist turns out not to bind.
- **The project's own `CLAUDE.md` gets auto-loaded.** The agent runs with `cwd=upload.dest`,
  which for Dinner Circle is a repo with a substantial `CLAUDE.md` written for a *developer*
  agent (build commands, lint conventions, architecture). It'll be read every run: useful app
  context, but also tokens spent on instructions irrelevant to browser testing, and possibly
  conflicting ones. If it proves noisy or expensive, the fix is running from a subdirectory or a
  scratch dir instead.
- **A long agent run can outlive its sandbox.** Start a big task 50 minutes into a 1-hour Hobby
  sandbox and it gets cut off mid-run -- and the STS credential expires on roughly the same
  clock. `extend` before a long run; the raw log means a cut-off run still leaves everything it
  got to. `run_agent` also takes an explicit wall-clock `timeout` rather than `None`, so a hung
  `claude -p` (stalled network, waiting on stdin) can't sit there consuming the whole sandbox
  lifetime.
